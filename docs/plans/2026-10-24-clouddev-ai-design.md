# CloudDev AI design

## Goal

Build a single-user developer workspace that combines a browser IDE, private Git service, PostgreSQL, OmniRoute, persistent storage, and a small authenticated launchpad. Local Compose is the first executable deployment target. Railway IaC and a Marketplace template follow without claiming a live deployment until one has been tested.

## Architecture

The project is a monorepo with four core services: `clouddev-ide`, `clouddev-git`, `clouddev-postgres`, and `clouddev-router`. A small `clouddev-launchpad` service is included for the requested first-run status and links. The launchpad uses its own generated credential and does not proxy or federate authentication. The IDE, Forgejo, and OmniRoute keep their own authentication boundaries.

The IDE is based on a pinned official code-server release and runs as an unprivileged user. A persistent IDE volume contains both the user home and `/workspace/projects`. Git credentials are a dedicated SSH key or scoped Forgejo user token. Forgejo uses PostgreSQL, disables open registration, requires sign-in to view content, and bootstraps its first administrator through the documented CLI without placing that administrator credential in the IDE.

OmniRoute is pinned to a verified release and image digest. Its SQLite state lives on its own volume. Its first administrator password and cryptographic secrets are generated by the Railway Template Composer or a local secret-generation script. Provider credentials remain in OmniRoute. The IDE receives only a separately scoped inference key after explicit onboarding. CLI wrappers fail closed when the gateway or key is unavailable and save model selection in the persistent home.

The launchpad links to the three authenticated services and displays their configuration and health state. It never receives provider master keys, Forgejo administrator tokens, or Railway credentials. Starting a coding agent still requires the user to run `ai-codex` or `ai-claude` in the IDE terminal; the launchpad will state this instead of pretending it can safely execute a shell command from a web button.

## Alternatives considered

1. One container for all services. Rejected because service upgrades, health checks, and persistent data ownership would be coupled.
2. Four services with no launchpad. This is the smallest stack, but it misses the requested guided entry point and leaves first-run links and checks undocumented in the product UI.
3. A public reverse proxy with every application under one origin. Rejected for V1 because it expands the authentication and path-routing surface and risks implying shared SSO. The applications retain separate native login flows.

## Data flow and security boundaries

The browser reaches the launchpad, IDE, Forgejo, and OmniRoute through Railway HTTPS domains. Service-to-service traffic uses Railway private DNS. PostgreSQL has no public domain. The IDE sends agent requests to OmniRoute over the private network. OmniRoute forwards prompts and code context to the provider selected by the operator. Provider processing may occur outside Railway EU West.

Railway private networking does not constrain outbound egress. The workspace will not mount a Docker socket, run as root, or receive a Railway platform token. Repository content and agent commands remain untrusted. An agent can read files available to the IDE user and can make outbound network requests. Its scoped gateway key is therefore a residual credential that can be used for inference by code running as that user.

No cross-service SSO is introduced. Local Compose runs over HTTP for development only; production depends on Railway HTTPS. MFA remains an application feature to be enabled and verified in each upstream service, not a claimed platform-wide guarantee.

## Persistence and operations

Separate persistent storage is used for IDE state, Forgejo repositories, PostgreSQL, and OmniRoute SQLite state. Stateful services remain single-replica. Backup instructions cover each store and require an actual restore test before any backup-success claim.

Railway IaC declares project resources, service variables, private references, regions, and volumes. Public generated domains and Marketplace onboarding must be finalized in the Railway Template Composer because the source file cannot invent a template ID or generated domain. The local Compose stack tests the service images and integration wiring independently of Railway.

## Verification

Tests cover configuration validation, launchpad authentication, absence of secret logging, service health, persistent data, private Forgejo repository round-trip, and mock-provider routing. Paid provider credentials are not used. Image builds and local integration checks are reported separately from a Railway deployment, Marketplace publication, provider acceptance, and a completed restore drill.
