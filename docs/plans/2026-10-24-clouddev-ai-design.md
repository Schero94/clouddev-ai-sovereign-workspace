# CloudDev AI design

## Goal

Build a single-user developer workspace that combines a browser IDE, private Git service, PostgreSQL, OmniRoute, persistent storage, and a small authenticated launchpad. Local Compose is the first executable deployment target. Railway IaC and a Marketplace template follow without claiming a live deployment until one has been tested.

## Architecture

The project has four Railway services: `clouddev-ide`, `clouddev-git`, `clouddev-postgres`, and `clouddev-router`. The always-on `clouddev-ide` runtime contains code-server, CloudCLI, the launchpad, Codex CLI, Claude Code CLI, Caddy, and OpenSSH. Caddy serves the mobile-first CloudCLI UI at `/`, code-server at `/vscode/`, and the launchpad at `/launchpad/` behind a private launchpad sign-in and signed HttpOnly session cookie. Its forward-auth check preserves CloudCLI's own Bearer authorization header. OpenSSH accepts public keys only on its explicit SSH port. CloudCLI, code-server, launchpad, and terminal agents use one persistent `/workspace` volume with `HOME=/workspace/home` and projects under `/workspace/projects`.

The IDE image is based on a pinned official code-server release. CloudCLI is installed from its pinned official npm package and shares the same home, projects, CLI session artifacts, and agent processes. Before each CloudCLI provider run, the hook reloads the scoped gateway config, writes the routed model to CloudCLI's session-model store, and passes that same model to the provider runtime. This keeps the reopened conversation's displayed model aligned with the model actually sent to OmniRoute. The Claude Agent SDK receives an explicit path to the pinned Claude Code executable. The browser-facing processes run as an unprivileged user. A narrowly scoped root startup step prepares the single workspace mount, persistent SSH host keys, and root-owned `authorized_keys`, then starts key-only sshd. Git uses a separate workspace identity key or scoped Forgejo user token. Forgejo uses PostgreSQL, disables open registration, requires sign-in to view content, and bootstraps its first administrator through the documented CLI without placing that administrator credential in the IDE.

OmniRoute is pinned to a verified release and image digest. Its SQLite state lives on its own volume. Its first administrator password and cryptographic secrets are generated by the Railway Template Composer or a local secret-generation script. Provider credentials remain in OmniRoute. The IDE receives only a separately scoped inference key after explicit onboarding. CLI wrappers fail closed when the gateway or key is unavailable and save model selection in the persistent home.

The embedded launchpad links to the workspace, Forgejo, and OmniRoute interfaces and displays their configuration and health state. Its trusted UID 1002 process receives the workspace login password and cookie-signing secret; neither value is passed to UID 1000 agents. It also displays only the public SSH fingerprint and recovery counts. It listens only on loopback. CloudCLI provides mobile agent chat and session management. The integrated terminal and native VS Code Remote-SSH use the same project tree and provider session files. The product does not promise identical editor window state.

## Alternatives considered

1. Separate desktop IDE and mobile agent services. Rejected because they would not share a guaranteed live filesystem or process/session state.
2. A single shared workspace service with CloudCLI, code-server, the launchpad, Caddy, and key-only OpenSSH. Selected because all clients operate on one runtime and one persistent mount. Caddy gates browser access with a signed session cookie verified by the trusted launchpad, while leaving CloudCLI's Bearer `Authorization` header intact. SSH uses public-key authentication; Forgejo and OmniRoute retain separate native accounts. Embedding the launchpad avoids another public service.
3. A separate Railway service for CloudCLI or the launchpad. Rejected because it would split the agent runtime, persistent home, active tasks, or first-run browser origin across service boundaries.

## Data flow and security boundaries

The browser reaches the shared workspace, Forgejo, and OmniRoute through authenticated Railway HTTPS domains. Caddy calls a loopback launchpad endpoint to verify the workspace cookie before it proxies CloudCLI, browser VS Code, and the launchpad. Native VS Code Remote-SSH reaches an explicitly exposed Railway TCP proxy for sshd on port 2222; it does not use `railway ssh`. Service-to-service traffic uses Railway private DNS. PostgreSQL has no public domain. The workspace sends agent requests to OmniRoute over the private network. OmniRoute forwards prompts and code context to the provider selected by the operator. Provider processing may occur outside Railway EU West.

Railway private networking does not constrain outbound egress. The workspace will not mount a Docker socket, run agent processes as root, or receive a Railway platform token. Repository content and agent commands remain untrusted. An agent can read files available to the IDE user and can make outbound network requests. Its scoped gateway key and workspace Git key are therefore residual credentials available to code running as that user. The public SSH identity is provisioned separately from the workspace, and its authorized key list is root-owned.

No cross-service SSO is introduced. Local Compose runs over HTTP for development only; production depends on Railway HTTPS. MFA remains an application feature to be enabled and verified in each upstream service, not a claimed platform-wide guarantee.

## Persistence and operations

Separate persistent storage is used for the shared workspace and CloudCLI session database, Forgejo repositories, PostgreSQL, and OmniRoute SQLite state. Railway permits one volume per service, prevents replicas for services with volumes, and stops overlapping deployments from mounting that volume. The workspace service therefore uses one volume rooted at `/workspace`, with home and projects as subdirectories. A runtime restart terminates in-flight processes. The task registry must record that work as interrupted and link to supported upstream session recovery. It must not claim the process kept running or silently replay a prompt. Backup instructions cover each store and require an actual restore test before any backup-success claim.

Railway IaC declares project resources, service variables, private references, regions, volumes, TCP proxy exposure for SSH, and `sleepApplication: false` for the workspace. The IaC DSL exposes networking and serverless settings, but generated HTTPS domains, variable generators, and Marketplace setup must be verified in the current pinned package and Composer workflow. No template ID is invented. The local Compose stack tests the service images and integration wiring independently of Railway.

## Verification

Tests cover configuration validation, browser authentication, key-only SSH policy, shared mount paths, task registry restart recovery, service health, persistent data, private Forgejo repository round-trip, and mock-provider routing. The cross-device acceptance flow must verify a desktop-started session can be reopened and continued on mobile, then be checked from native VS Code using the same files. Paid provider credentials are not used. Image builds and local integration checks are reported separately from native desktop/iPhone/Windows acceptance, a Railway deployment, Marketplace publication, provider acceptance, and a completed restore drill.
